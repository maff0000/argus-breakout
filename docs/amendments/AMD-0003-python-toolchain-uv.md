## 1. Problem
PID-ARGUS-0001 §8.1 mandates Python 3.12; the delivery host has 3.11 and
the Delivery Controller may not install system packages. The PID said
nothing about how the interpreter is provided. That is an architectural
gap, correctly returned.

## 2. Change
- **PID §8.1** gains the paragraph "Toolchain (ADR-0007)": uv installed
  project-locally under `/srv/argus-breakout-tools/`, uv-managed CPython
  3.12, `uv.lock` as the lockfile, `uv run` for every command; see ADR-0007
  for the exact layout.
- **PID §12**: "`uv run python -m pytest -q`" replaces "`python -m pytest -q`"
  (equivalent inside the venv).
- **WO-0001 §2**: `requirements.lock` → `uv.lock` (generated by `uv lock`);
  CI job uses `astral-sh/setup-uv` + `uv sync --all-extras` + `uv run …`.
  **AC5** becomes: "`uv.lock` exists and `uv sync --all-extras` from a clean
  checkout succeeds (operator check)." **AC1** becomes: "`uv venv --python
  3.12 .venv && uv sync --all-extras` succeeds; `.venv/bin/python --version`
  reports 3.12.x (operator check)."
- **WO-0009 §2** runbook: install steps use the ADR-0007 procedure; the
  tools directory is mode 0755; the service unit keeps
  `ExecStart=/srv/argus-breakout/ops/nightly.sh` which execs
  `/srv/argus-breakout/.venv/bin/argus`.
- **Prompts**: Delivery Controller test commands become `uv run python -m
  pytest -q`, `uv run ruff check .`; Implementer and Auditor prompts gain an
  "Environment" line: prepend `/srv/argus-breakout-tools/bin` to `PATH`,
  create the worktree venv with `uv venv --python 3.12 .venv && uv sync
  --all-extras`, run everything via `uv run`.

## 3. Consequences
No change to application behaviour, tests (other than invocation), or
acceptance semantics. Step 0 of the kickoff gains the toolchain install,
performed by the Delivery Controller under ADR-0007 with version and
checksum recorded in `docs/evidence/HOST-SETUP.md`.
